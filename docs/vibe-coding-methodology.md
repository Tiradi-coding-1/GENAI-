## 1. 什麼是 Vibe Coding

Vibe Coding 是一種以 AI 工具為核心驅動力的軟體開發方法論。開發者透過「描述意圖 (Prompt)」而非「手動編碼」來完成軟體開發，將不同階段的任務分配給最適合的 AI 工具，形成一條完整的 AI 工具鏈。

### 核心理念

| 傳統開發 | Vibe Coding |
|---------|-------------|
| 手動逐行編寫程式碼 | 以 Prompt 描述需求，AI 生成程式碼 |
| 開發者負責所有技術細節 | 開發者專注於需求描述與品質把關 |
| 單一工具 (IDE) 為主 | 多 AI 工具協作，各司其職 |
| 線性開發流程 | Phase 化、可追蹤的迭代流程 |

## 3. Phase 分解與執行流程

### Phase 0：專案初始化與環境建立

- **輸入**：藍圖規格描述
- **AI 工具**：minimax m2.5
- **產出**：資料夾結構、requirements.txt、.gitignore
- **Prompt 策略**：直接描述專案結構需求，指定 Python 版本與所需套件

```
執行流程：
1. 描述專案目標與技術棧
2. AI 生成資料夾結構與初始檔案
3. 執行 pip install 驗證環境
4. Git commit 記錄
```

### Phase 1：股票族群研究與分類

- **輸入**：「台灣 AI 與半導體概念股」分類需求
- **AI 工具**：Google Search
- **產出**：3 個子族群，每族群 5 檔股票 + 入選理由
- **Prompt 策略**：搜尋台股各族群成分股，交叉比對產業地位

```
分類標準：
├── 族群一：晶圓代工與先進封裝 (上游製造)
├── 族群二：AI 伺服器與 ODM 代工 (中游組裝)
└── 族群三：AI 散熱與電源管理 (下游零組件)
```

### Phase 2：台股 OHLCV 數據抓取

- **輸入**：股票清單 + data_fetcher 規格 Prompt
- **AI 工具**：minimax m2.5
- **產出**：3 個族群 CSV 檔案
- **Prompt 策略**：明確指定 API、欄位格式、容錯機制、速率控制

```
關鍵 Prompt 要素：
├── 使用 yfinance 而非直接爬蟲
├── 時間範圍：今天往回推 180 天
├── 長表格式：每列 = 一檔股票 + 一天
├── try-except 容錯 + retry 3 次
└── sleep 1.5 秒防止限流
```

### Phase 3：K 線圖繪製

- **輸入**：CSV 數據 + visualizer 規格 Prompt
- **AI 工具**：minimax m2.5
- **產出**：3 張族群 K 線圖 PNG
- **Prompt 策略**：指定圖表風格、配色、均線參數、subplot 排版

```
關鍵 Prompt 要素：
├── 使用 mplfinance 而非手繪
├── 台灣配色：紅漲綠跌
├── 均線：MA5 橘色 + MA20 藍色
├── subplot 垂直排列同族群股票
└── 中文字體相容性處理
```

### Phase 4：圖表趨勢分析

- **輸入**：3 張 K 線圖 PNG + 分析 Prompt
- **AI 工具**：Gemini 3 Pro (視覺 AI)
- **產出**：docs/analysis.md 趨勢分析報告
- **Prompt 策略**：角色設定為「台股技術分析師」，指定分析框架

```
分析框架：
├── 整體趨勢判斷
├── 均線訊號 (黃金交叉/死亡交叉)
├── 量價關係 (價漲量增/價跌量縮)
├── 族群內個股強弱排序
└── 操作結論建議
```

### Phase 5：README 與文件化

- **輸入**：整份專案內容
- **AI 工具**：Claude Sonnet 4.6
- **產出**：README.md、架構文件
- **Prompt 策略**：提供完整專案脈絡，要求結構化輸出

## 4. Prompt 工程實踐

### 4.1 Prompt 設計原則

本專案的 Prompt 設計遵循以下原則：

1. **角色設定 (Role)**：為 AI 指定專業身分（如「台股技術分析師」）
2. **明確規格 (Specification)**：列出必備欄位、格式、參數
3. **限制條件 (Constraints)**：指定技術限制（如 retry 次數、sleep 間隔）
4. **輸出格式 (Output Format)**：指定 Markdown 標題層級、表格格式
5. **驗收標準 (Acceptance Criteria)**：可量化的成功判斷條件

### 4.2 Prompt 範例對照

| Phase | Prompt 關鍵句 | 為何有效 |
|-------|-------------|---------|
| Phase 2 | 「實作 try-except，失敗時印出警告繼續執行（不崩潰）」 | 明確容錯行為，避免 AI 生成會崩潰的程式 |
| Phase 3 | 「K 線顏色：上漲紅色、下跌綠色（台灣習慣）」 | 指定在地化需求，避免使用國際慣例（綠漲紅跌） |
| Phase 4 | 「你現在是一位台股技術分析師」 | 角色設定提高分析專業度與格式一致性 |

## 5. 遇到的挑戰與解決方案

### 5.1 中文字體顯示問題

**問題**：mplfinance 在 Windows 環境下繁體中文顯示為方塊。

**解決**：設定 matplotlib 字體 fallback 鏈：
```python
matplotlib.rcParams["font.family"] = [
    "Adobe Fan Heiti Std",
    "Microsoft JhengHei",
    "SimHei",
    "Arial Unicode MS",
    "sans-serif"
]
```

### 5.2 部分股票無數據

**問題**：部分股票（如 3324.TW 雙鴻）偶爾無法透過 yfinance 取得數據。

**解決**：
- `fetch_stock_data` 回傳 `None` 時跳過，不中斷流程
- `fetch_group_data` 用 list 收集成功結果再 concat
- 印出警告訊息供人工確認

### 5.3 yfinance API 限流

**問題**：連續快速請求會被 Yahoo Finance 暫時封鎖。

**解決**：
- 每次 API 請求後 `time.sleep(1.5)`
- 網路錯誤自動 retry 最多 3 次
- retry 間 delay 1.5 秒

### 5.4 Plan 與實作的落差

**問題**：Phase 2、3 的 Implementation Plan 設計了 class-based 架構，但實際實作改用 function-based 架構。

**原因**：function-based 在此規模下更簡潔直覺，減少不必要的抽象層。這是 Vibe Coding 中常見的「Plan → Execute → Adapt」循環，開發者在執行過程中根據實際情況調整。

## 6. Vibe Coding 流程反思

### 6.1 成功經驗

| 項目 | 說明 |
|------|------|
| AI 工具分工明確 | 每個 Phase 選擇最適合的工具，發揮各自優勢 |
| Phase 化管理 | 6 個 Phase 各有明確輸入/輸出，便於追蹤進度 |
| Prompt 規格化 | 用條列式規格描述需求，減少 AI 理解偏差 |
| TDD 驅動 | 先寫測試再寫程式碼，降低 AI 生成程式碼的品質風險 |
| Git 版本控制 | 每個 Phase 完成後 commit，保留完整開發歷程 |

### 6.2 改進方向

| 項目 | 建議 |
|------|------|
| 股票清單確認 | Phase 1 應在專案開始前獨立確認，避免後續修改 |
| 錯誤日誌 | data_fetcher 可加入 logging 模組取代 print |
| 圖表尺寸 | 各族群圖表應統一固定尺寸，提高報告一致性 |
| 自動化程度 | 可考慮加入 Makefile 或 shell script 串接全流程 |
| 數據快取 | 加入 CSV 快取機制，避免重複抓取 |

---

## 7. 結論

Vibe Coding 的核心價值在於：**讓開發者從「寫程式的人」轉變為「描述需求並把關品質的人」**。本專案證明了透過精確的 Prompt 設計與合適的 AI 工具選擇，即使是涉及 API 串接、數據處理、圖表繪製與技術分析的複雜專案，也能在短時間內高品質完成。

關鍵成功因素：
1. 清楚的 Phase 分解，降低每次 AI 互動的複雜度
2. 精確的 Prompt 規格，減少來回修改次數
3. 適材適所的 AI 工具選擇，發揮各工具長處
4. 持續的品質把關（TDD + 人工驗收）
